# Question-Driven Framework для Mobile System Design (Android + KMP)

> Фреймворк для прохождения интервью по mobile system design. Идея: любой кейс решается
> последовательностью вопросов — себе и интервьюеру. Каждый вопрос открывает ветку,
> каждая ветка заканчивается рекомендацией: какой подход или технология подходит и почему.
>
> Составлен на основе анализа: weeeBox/mobile-system-design (де-факто стандарт индустрии),
> «Mobile System Design Interview» (Manuel Vivo), «Cracking the Mobile System Design Interview»,
> материалов ProAndroidDev, System Design Handbook, ByteByteGo, HelloInterview,
> Grokking the Mobile System Design Interview (Artem Goncharov), документации Kotlin Multiplatform
> и разборов реальных интервью FAANG. Полный список источников — в конце документа.

## 0. Как пользоваться фреймворком

### Тайминг интервью (45–60 минут)

| Время | Этап | Что делаешь |
|---|---|---|
| 2–5 мин | Знакомство | Коротко о релевантном опыте, без «гуру»-самоописаний |
| ~5 мин | Требования | Вопросы из Шага 1, фиксируешь скоуп письменно |
| ~10 мин | High-level | Диаграмма из Шага 2, проговариваешь потоки данных |
| 20–30 мин | Deep dive | 2–3 ветки из Шага 3 — те, что важны для кейса, или те, куда ведёт интервьюер |
| ~5 мин | Вопросы интервьюеру | Заготовь 2–3 вопроса про команду/стек |

### Главный принцип

На каждом шаге ты **сначала задаёшь вопрос** (интервьюеру — если ответ зависит от продукта;
себе — если это инженерное решение), **затем перечисляешь 2–3 варианта с трейд-оффами**,
**затем принимаешь решение и объясняешь почему**. Формула ответа:

> «Здесь есть варианты A, B, C. Для наших требований X и Y я выбираю B, потому что…
> Минус B — Z, мы его компенсируем так-то.»

Никогда не отвечай «потому что так рекомендует документация» и не жди валидации
(«так нормально?») — решай сам и защищай решение. Интервью — это сотрудничество,
а не экзамен: думай вслух, реагируй на подсказки интервьюера (подсказка = ты ушёл не туда).

### Как читать ветки

Каждая ветка оформлена так:

- **Q:** вопрос, который ты задаёшь.
- Варианты ответов → под каждым: что это значит для дизайна и какая технология подходит.
- **Рекомендация по умолчанию** — если интервьюеру всё равно или времени мало.

## 1. ШАГ 1 — Скоуп и требования

Цель: за 5 минут превратить размытое «спроектируй X» в письменный список из
3–5 функциональных требований, 3–4 нефункциональных и явного out-of-scope.
Записывай всё — на доске/в редакторе, это твой контракт с интервьюером.

### 1.1 Q: Какой скоуп задачи?

> «Мы проектируем только клиент при готовом API, клиент + API, или клиент + API + бэкенд?»

| Ответ | Что это значит |
|---|---|
| **Только клиент** | Весь фокус на архитектуру приложения, кэширование, UI, офлайн. API дан — но ты можешь предложить его улучшить |
| **Клиент + API** (самый частый) | Проектируешь контракт: эндпоинты, схемы, пагинацию, real-time канал. Бэкенд — «чёрный ящик» |
| **Клиент + API + бэкенд** | Редко для мобильной позиции. Держи наготове: LB → app servers → cache (Redis) → DB (+ CDN, message queue). Глубоко не закапывайся — скажи, что готов, но фокус мобильный |

**Рекомендация:** если интервьюер не уточняет — проговори, что фокусируешься на клиенте
и контракте API, а бэкенд считаешь абстракцией. Это ожидание мобильного интервью.

### 1.2 Q: Это приложение или библиотека/SDK?

Кейсы бывают двух типов, и подход у них разный:

- **Приложение** (лента, чат, фотоапп): ветки — API, хранение, офлайн, UI.
- **Библиотека/SDK** (file downloader, image loader, analytics SDK, pagination library):
  главные ветки — **публичный API библиотеки** (façade, builder, конфигурация), управление
  ресурсами (пулы потоков, лимиты параллелизма), жизненный цикл (кто владеет, как отменять),
  минимизация зависимостей, интеграция в чужие приложения (size impact, R8-правила),
  обратная совместимость. См. раздел [5](#5-типовые-кейсы-прогон-через-фреймворк).

### 1.3 Функциональные требования

Q к интервьюеру: «Какие 3–5 фич обязательны?» Если отдают на откуп тебе — выбери сам
и проговори. Пример для «лента Twitter»:

1. Бесконечная лента постов (текст + изображения).
2. Лайк поста.
3. Просмотр комментариев (read-only).

Явно вынеси **out of scope**: логин/регистрация, создание постов, подписки, аналитика —
«считаю вне скоупа, вернёмся, если останется время». Это защита от расползания
и признак зрелости.

### 1.4 Нефункциональные требования — дерево вопросов

Задай их подряд, ответы определяют весь дальнейший дизайн:

**Q1: Нужен ли офлайн-режим? Какого уровня?**
- «Нет, только онлайн» → простой HTTP-кэш, показываем заглушку без сети.
- «Читать закэшированное» → БД как кэш, stale-while-revalidate. (Уровень по умолчанию.)
- «Полноценно работать офлайн, включая запись» → offline-first, очередь операций,
  разрешение конфликтов → ветка [3.5](#35-offline-first-и-синхронизация).

**Q2: Нужен ли real-time?**
- «Нет / при открытии экрана» → pull при входе + pull-to-refresh.
- «Да, обновления в реальном времени» → ветка [3.2](#32-real-time-доставка-обновлений-на-клиент):
  SSE / WebSocket / push. Уточни: нужен ли real-time в фоне (тогда push обязателен).

**Q3: Каков масштаб? (DAU, размер команды)**
- Миллионы DAU → на клиенте: exponential backoff + jitter, rate limiting,
  защита от self-DDoS (не ретраить агрессивно при 5xx), CDN для медиа.
- Команда 2–4 человека → простая модульность, один репозиторий.
- Команда 20–100+ → мультимодульность по фичам, api/impl-разделение модулей,
  договорённости о владении кодом, demo-приложения на фичу.

**Q4: Целевые рынки и устройства?**
- Развивающиеся рынки → дорогой трафик и слабые устройства: минимизируй размер APK
  (App Bundle, R8, ресурсы по конфигурациям), агрессивный кэш, лёгкие форматы (WebP/AVIF),
  режим экономии данных, поддержка старых API level.
- Только флагманы/один рынок → можно Compose-only, minSdk повыше, тяжёлые анимации.

**Q5: Какие платформы?**
- Только Android → классический стек.
- Android + iOS одной командой / шаринг логики → ветка [KMP](#4-ветка-kmp--kotlin-multiplatform).
- + планшеты/foldables → адаптивные лейауты, list-detail.

**Q6: Требования к консистентности данных?**
- Eventual consistency допустима (лайки, счётчики) → optimistic updates, фоновая синхронизация.
- Строгая (деньги, бронирования, остатки) → никакого optimistic UI на критичных операциях,
  подтверждение сервером, идемпотентность, блокировки на сервере (например, лок места
  при бронировании билета).

**Q7: Как часто меняются данные?**
- Редко → обычный pull, длинный TTL кэша.
- Очень часто (биржевые котировки, live-скоры) → SSE/WebSocket, иначе polling задушит сервер.

**Q8: Какие медиа? Размеры?**
- Картинки → форматы, ресайз на CDN, ветка [3.6](#36-изображения-и-медиа).
- Видео → стриминг HLS/DASH, ExoPlayer/Media3, prefetch.
- Загрузка больших файлов → resumable/chunked upload.

**Q9: Чувствительные данные? (PII, платежи, медицина)**
- Да → шифрование at rest, Keystore/Keychain, certificate pinning, никакой критичной
  логики на клиенте → ветка [3.11](#311-безопасность-и-приватность).

### 1.5 Back-of-the-envelope расчёты (по желанию, 1–2 минуты)

Нужны, только если из них следует решение. Примеры:

- **Размер кэша ленты:** пост ≈ 1–2 КБ JSON + превью 50–100 КБ. 500 постов ≈ 25–50 МБ
  картинок → лимит дискового кэша изображений 200–400 МБ разумен, БД — 500 записей с LRU.
- **Трафик polling'а:** 1 запрос/мин × 10 млн клиентов = ~166k RPS только на проверку
  обновлений → аргумент за push/SSE.
- **Чат:** 40 сообщений/день × 1 КБ = мелочь по трафику; главное — латентность и доставка,
  а не пропускная способность.

Формула вывода: «Из расчёта следует, что узкое место — X, поэтому проектируем Y».

## 2. ШАГ 2 — High-level архитектура

Цель: одна диаграмма «большой картины» без лишних деталей. Проговори каждый блок
и поток данных. Не рисуй 20 боксов — 8–12 достаточно.

### 2.1 Серверная часть (как чёрные ящики)

```
[Backend API] ── [Push Provider (FCM/APNs)] ── [CDN для медиа]
```

- **Backend API** — весь сервер одним боксом (если скоуп клиентский).
- **Push Provider** — FCM (Android/кроссплатформенно), APNs (iOS). Нужен, если есть
  real-time в фоне или нотификации.
- **CDN** — статика и медиа; клиент ходит за картинками напрямую в CDN по URL из API.

### 2.2 Клиентская часть — слои

```
┌────────────────────────── UI Layer ──────────────────────────┐
│  Screens (Compose) · ViewModel/StateHolder · Navigation      │
└──────────────────────────────┬───────────────────────────────┘
┌────────────────────────── Domain ────────────────────────────┐
│  UseCases / Interactors · доменные модели · бизнес-правила   │
└──────────────────────────────┬───────────────────────────────┘
┌────────────────────────── Data Layer ────────────────────────┐
│  Repository (SSOT-медиатор)                                  │
│    ├── API Service (Retrofit/Ktor)  ── сеть                  │
│    ├── Persistence (Room/SQLDelight) ── локальная БД         │
│    └── Sync Engine / RemoteMediator ── склейка сети и кэша   │
└──────────────────────────────────────────────────────────────┘
Сквозные: DI-граф (Hilt/Koin) · Image Loader (Coil) · Analytics ·
Logger · Config/Feature Flags · Background Scheduler (WorkManager)
```

Ключевые тезисы, которые надо проговорить:

- **Repository — единственная точка доступа к данным** для домена/UI; он решает,
  откуда брать данные (кэш vs сеть) и куда писать.
- **Локальная БД — Single Source of Truth (SSOT):** UI подписан на БД (Flow),
  сеть только обновляет БД. Это даёт офлайн и консистентность бесплатно.
- **Однонаправленный поток данных (UDF):** события вверх, состояние вниз.
- **DI** для тестируемости и модульности: Hilt (Android-only), Koin/kotlin-inject (KMP).

### 2.3 Q: Одна фича или всё приложение? Модульность

- Кейс про одну фичу → покажи модуль фичи внутри слоёв.
- Кейс про приложение + большая команда → мультимодульность:
  `:app`, `:core:network`, `:core:database`, `:core:designsystem`, `:feature:feed`,
  `:feature:details`… Каждая фича — самодостаточный модуль со своим DI-подграфом.
  Плюсы: параллельная разработка, инкрементальная сборка, чёткие границы.

### 2.4 Что оценивает интервьюер на этом этапе

- Умение показать big picture без утопания в деталях.
- Названы главные блоки и **как они взаимодействуют** (нарисуй стрелки, проговори
  сценарий: «пользователь открывает ленту → ViewModel просит Repository → Repository
  отдаёт кэш из БД и параллельно триггерит сеть → ответ пишется в БД → UI обновляется
  через подписку»).
- Модульность и работа в команде.

После диаграммы спроси: **«Куда пойдём глубже — API, хранение, офлайн или UI?»** —
это отдаёт контроль интервьюеру и экономит время на важное.

## 3. ШАГ 3 — Deep dive: ветки решений

Выбери 2–3 ветки, критичные для кейса (или куда ведёт интервьюер), и пройди их
по схеме «вопрос → варианты → решение».

### 3.1 Сетевой слой и дизайн API

#### Q: Какой протокол общения с сервером?

| Протокол | Плюсы | Минусы | Когда выбирать |
|---|---|---|---|
| **REST + JSON** | Простота, HTTP-кэширование, стейтлес, все умеют, человекочитаемо | Over-/under-fetching, нет схемы «из коробки», оверхед заголовков | **Дефолт** для CRUD-приложений: лента, каталог, профиль |
| **GraphQL** | Клиент запрашивает ровно нужные поля, строгая схема, subscriptions, меньше версионирования | Сложный бэкенд, сложное кэширование, связывание клиента с сервером | Много разных клиентов/экранов с разными наборами полей; когда бэкенд уже на GraphQL (Apollo Kotlin) |
| **gRPC (protobuf)** | Компактные бинарные сообщения, схема, стриминг, HTTP/2-мультиплексирование | Не человекочитаемо, тяжелее клиент, порог входа | Внутренние API, высокие требования к латентности/трафику, IoT |
| **WebSocket** | Полный дуплекс, низкая латентность | Держит соединение (батарея), сложное масштабирование, файрволы | Чат, игры, совместное редактирование — см. 3.2 |
| **MQTT** | Сверхлёгкий pub/sub, QoS-уровни | Нужен брокер, узкая ниша | IoT, мессенджеры с экономией батареи (так делал Facebook Messenger) |

**Рекомендация по умолчанию:** REST + JSON поверх HTTPS; для real-time — отдельный канал
(3.2). Упомяни gRPC/GraphQL как альтернативу и объясни, почему не берёшь.

#### Q: Как выглядит контракт? (напиши 2–4 эндпоинта)

Пример для ленты:

```
GET /v1/feed?limit=20&cursor=<opaque>      → { items: [...], next_cursor, prev_cursor }
POST /v1/posts/{id}/like                    Idempotency-Key: <uuid>
GET /v1/posts/{id}/comments?limit=20&cursor=...
```

Проговори: версионирование (`/v1`), авторизация (`Authorization: Bearer <JWT>`),
идемпотентность мутаций, коды ошибок (401 → refresh, 429 → backoff по `Retry-After`).

#### Q: Как устроена аутентификация на клиенте?

- Access token (короткоживущий JWT) + refresh token.
- Хранение: **Keystore/EncryptedSharedPreferences (Android), Keychain (iOS),
  в KMP — expect/actual поверх обоих**. Никогда — в plain SharedPreferences.
- **Token refresh:** OkHttp `Authenticator` (или Ktor `Auth` plugin) перехватывает 401,
  обновляет токен **с mutex'ом** (один refresh на все параллельные запросы), при провале —
  логаут. Упомяни гонку одновременных 401 — это любимый вопрос.

#### Q: Как обрабатываем ошибки и ретраи?

- Классифицируй: сетевые (retry уместен), 4xx (не ретраим, чиним запрос), 5xx/429
  (retry с **exponential backoff + jitter**, уважаем `Retry-After`).
- Ограничь число ретраев; на массовых клиентах без jitter получишь thundering herd.
- Мутации ретраим только с Idempotency-Key.
- В коде: sealed class `Result`/`Either` из репозитория, а не исключения до UI.

#### Q: Чем реализуем сетевой слой?

- **Android-only:** Retrofit + OkHttp (+ kotlinx.serialization/Moshi), интерсепторы
  для auth/логирования, HTTP-кэш OkHttp.
- **KMP:** **Ktor Client** (движки: OkHttp на Android, Darwin на iOS) +
  kotlinx.serialization; плагины Auth, ContentNegotiation, HttpRequestRetry, Logging.
- GraphQL → Apollo Kotlin (KMP-ready). gRPC → grpc-kotlin (KMP-поддержка через Wire/connect).

#### Q: Нужна ли приоритизация запросов (QoS)?

Если приложение шлёт много запросов (лента + прогрузка картинок + аналитика):
- Раздели трафик: **user-critical** (то, что на экране) → сразу; **prefetch** → низкий
  приоритет; **аналитика/логи** → батчинг и отложенная отправка через WorkManager.
- Лимит параллелизма (OkHttp Dispatcher: maxRequests, maxRequestsPerHost),
  отмена запросов при уходе с экрана (structured concurrency: scope у ViewModel).

### 3.2 Real-time: доставка обновлений на клиент

#### Q: Насколько «реальное» время нужно и в каком состоянии приложения?

Дерево решений:

1. **Обновления нужны, когда приложение закрыто/в фоне?**
   - Да → **Push (FCM/APNs)** обязателен как канал пробуждения. Помни: не гарантирован,
     возможны задержки; шли «сигнал» (data push), а данные тяни через API (или клади
     payload, если маленький).
2. **Приложение на экране; допустима задержка в минуты?**
   - Да → **short polling** каждые N минут или refresh при `onStart`. Просто, стейтлес,
     дружит с балансировщиками. Минус: латентность, лишний трафик.
3. **Нужны секунды, поток только сервер → клиент?**
   - → **SSE (Server-Sent Events)**: однонаправленный стрим поверх обычного HTTP,
     авто-reconnect с `Last-Event-ID`, проще WebSocket. Идеально: лайки/счётчики в ленте,
     live-скоры, котировки. (OkHttp EventSource; в Ktor — плагин SSE.)
4. **Нужен двунаправленный обмен с низкой латентностью?**
   - → **WebSocket**: чат, совместное редактирование, игры. Проговори: heartbeat
     ping/pong (10–30 с), reconnect с exponential backoff + jitter, resume
     (клиент шлёт `last_received_id`, сервер досылает пропущенное), деградация в polling.
5. **Long polling** — упоминай как legacy/fallback, когда WebSocket/SSE недоступны.

**Классическая связка (лента/чат):** WebSocket или SSE, пока приложение активно,
+ FCM/APNs для фона. Проговори стоимость: постоянное соединение ест батарею →
разрывай его в фоне (lifecycle-aware connection manager).

#### Q: Как гарантируем доставку и порядок сообщений? (чат)

- Монотонные ID/sequence на сервере; клиент хранит `last_message_id` per-чат
  и при reconnect запрашивает дельту (`GET /messages?after=<id>`).
- ACK: sent (получен сервером) → delivered (получен устройством) → read.
- Дедупликация по client-generated UUID сообщения (сообщение локально создаётся
  со статусом PENDING в БД, отправляется, при ретрае сервер дедуплицирует).

### 3.3 Пагинация

#### Q: Какой тип пагинации?

| Тип | Как | Плюсы | Минусы | Когда |
|---|---|---|---|---|
| **Offset** (`?offset=40&limit=20`) | Пропустить N | Просто, случайный доступ к странице | Медленно на больших offset, **сдвиг страниц** при вставках/удалениях | Маленькие статичные списки, админки |
| **Keyset** (`?after_date=...`) | WHERE поле > значения | Быстро, устойчиво к вставкам | Только по индексированному упорядоченному полю, раскрывает схему | Списки, отсортированные по времени/ID |
| **Cursor / opaque token** (`?cursor=abc123`) | Сервер отдаёт непрозрачный курсор | Скрывает реализацию, переживает вставки/удаления, сервер может менять логику | Курсор истекает, нет random access, нельзя «страницу 5» | **Дефолт для лент и бесконечного скролла** |

**Рекомендация:** cursor-based для любых лент. Размер страницы ~20 (первая страница
может быть меньше для быстрого first paint), `limit` подбирается по вьюпорту.

#### Q: Как пагинация устроена на клиенте?

- **Android:** Paging 3 + **RemoteMediator**: Room — SSOT, RemoteMediator тянет страницы
  из сети и пишет в БД, `PagingSource` читает из БД. Получаешь офлайн, плейсхолдеры,
  ретраи из коробки. Честно скажи о сложности API Paging 3 — можно и руками:
  ViewModel следит за «до конца списка осталось K элементов» → просит следующую страницу.
- **KMP:** своя реализация Pager в common (в KMP Paging 3 доступен через
  app.cash.paging — мультиплатформенный форк) поверх SQLDelight.
- Проговори: prefetch distance, дедупликация запросов страницы (in-flight guard),
  сохранение позиции скролла при повороте/процессе-смерти, pull-to-refresh
  (инвалидация с новым курсором, не очищай кэш до успешного ответа).

### 3.4 Локальное хранение данных

#### Q: Какие данные храним? → выбор хранилища по типу данных

| Тип данных | Хранилище (Android) | KMP-эквивалент |
|---|---|---|
| Флаги, настройки, маленькие key-value | **Jetpack DataStore** (Preferences/Proto; SharedPreferences — legacy) | multiplatform-settings, DataStore KMP |
| Структурированные/пагинированные данные, ленты, чаты | **Room** (SQLite + ORM, миграции, Flow) | **SQLDelight** (typesafe SQL, Flow) или Room KMP (с 2.7 поддерживает iOS) |
| Токены, ключи, пароли | **Keystore + EncryptedSharedPreferences** | expect/actual: Keystore ↔ Keychain |
| Большие файлы, медиа | Файловая система (internal cache dir) | okio + expect/actual пути |
| Кастомная бинарная сериализация | Proto DataStore / protobuf-файлы | kotlinx.serialization + okio |

Realm/ObjectBox — упомяни как альтернативу (объектная БД, KMP-поддержка у Realm),
но дефолт индустрии — Room/SQLDelight.

#### Q: Где физически храним и что случится при удалении приложения?

- **Internal storage** — песочница, приватно, удаляется с приложением. Дефолт.
- **Cache directory** — система может очистить при нехватке места → только
  восстановимые данные (картинки, превью).
- **External/Shared storage** — только по необходимости (экспорт пользователю),
  на Android — через MediaStore/SAF (scoped storage).

#### Q: Политика кэша: размер, устаревание, вытеснение?

- Лимиты: БД ленты — например, 500 записей; дисковый кэш картинок — 200–400 МБ.
- Вытеснение: **LRU** (дефолт), TTL для данных с истекающей актуальностью,
  LFU — редко.
- Инвалидация: по TTL + принудительно по push/событию + при pull-to-refresh.
- Стратегии чтения/записи: **read-through** (смотрим кэш → промах → сеть → пишем в кэш),
  **stale-while-revalidate** (мгновенно отдаём устаревшее, в фоне обновляем — лучший UX
  для лент), write-through для настроек.
- Чувствительное в кэше — шифровать (SQLCipher для БД, ключи в Keystore) или не кэшировать.

#### Q: Миграции и версии схемы?

Room: `Migration(1,2)` + автотесты миграций; SQLDelight — `.sqm`-файлы.
Скажи про план на «схема сломалась»: destructive fallback только для чистого кэша.

### 3.5 Offline-first и синхронизация

#### Q: Какой уровень офлайна требуется? (задай в Шаге 1, здесь раскрываешь)

**Уровень 1 — читать кэш.** БД = SSOT, stale-while-revalidate, баннер «нет сети»
(ConnectivityManager / NWPathMonitor через expect/actual в KMP).

**Уровень 2 — писать офлайн (optimistic updates).**
- Мутация мгновенно применяется в локальной БД (лайк подсветился) со статусом `PENDING`.
- Операция кладётся в **очередь операций** (таблица outbox в той же БД, в той же
  транзакции — паттерн transactional outbox).
- **WorkManager** (constraint: NetworkType.CONNECTED, backoff policy) выгребает очередь
  при появлении сети; на iOS-стороне KMP — BGTaskScheduler/немедленная отправка при запуске.
- Каждой операции — client-generated UUID → **Idempotency-Key**, сервер дедуплицирует
  ретраи.
- При фейле: откат локального изменения + уведомление пользователя, либо пометка
  «не отправлено, повторить».
- UI показывает pending-состояния (часики у сообщения в чате).

**Уровень 3 — полноценная двусторонняя синхронизация (заметки, документы, несколько устройств).**

#### Q: Как разрешаем конфликты?

| Стратегия | Суть | Когда |
|---|---|---|
| **Last-Write-Wins (LWW)** | Побеждает поздний timestamp | Просто, но теряет данные; ок для настроек, статусов. Часы клиента ненадёжны → серверный timestamp/версии |
| **Версии + server authority** | Клиент шлёт `base_version`; сервер сравнивает, при расхождении возвращает 409 + актуальную версию | **Дефолтная рекомендация**: сервер — арбитр, клиент перечитывает и мержит/повторяет |
| **Ручное разрешение (UI)** | Показать пользователю обе версии | Критичные пользовательские данные (заметки) |
| **OT / CRDT** | Автоматический мерж конкурентных правок | Совместное редактирование (Google Docs, Figma). Назови, объясни цену: сложность реализации |

Дельта-синхронизация: тянем не всё, а изменения после `last_sync_token`
(`GET /changes?since=<token>`), сервер отдаёт upserts + tombstones (удаления).

### 3.6 Изображения и медиа

#### Q: Как грузим и кэшируем изображения?

- Библиотека: **Coil** (Compose-first, с Coil 3 — KMP), Glide (Android legacy);
  за фасадом-интерфейсом `ImageLoader`, чтобы можно было подменить.
- Двухуровневый кэш: memory (LruCache, ~15–25% доступной памяти) + disk (LRU, лимит).
- **Downsampling под размер вью** — не декодируй 4000×3000 в аватарку 100×100.
- Форматы: WebP/AVIF (меньше JPEG на 25–50%); сервер/CDN отдаёт варианты размеров
  (`?width=`) — клиент просит нужный.
- UX списка: placeholder/blurhash → низкое разрешение → полное; отмена загрузки
  при recycle; prefetch следующих элементов при скролле.
- В KMP: Coil 3 / Kamel в common-коде.

#### Q: Видео?

- **Media3/ExoPlayer**, адаптивный стриминг **HLS/DASH** (сегменты + манифест,
  качество подстраивается под канал), CDN.
- Prefetch первых секунд следующего видео в ленте (как TikTok), пул плееров,
  пауза при уходе из вьюпорта.

#### Q: Загрузка (upload) больших файлов?

- **Chunked + resumable upload**: файл бьётся на чанки (например, 5 МБ),
  `POST /uploads` создаёт сессию → чанки с указанием offset → сервер отвечает,
  что получил → при обрыве продолжаем с последнего подтверждённого чанка
  (протоколы: tus, Google resumable upload).
- Через WorkManager (unmetered/charging constraints по требованиям), уведомление
  с прогрессом (foreground service type dataSync при необходимости).
- Компрессия/транскодирование перед отправкой; EXIF-стриппинг для приватности.

### 3.7 UI-слой и архитектура презентации

#### Q: Какой презентационный паттерн?

| Паттерн | Суть | Когда |
|---|---|---|
| **MVVM** | ViewModel держит state (StateFlow), UI подписан | **Дефолт**; официальная рекомендация Google |
| **MVI** | Единый immutable `UiState`, поток `Intent → Reducer → State`, строгий UDF | Сложные экраны с большим числом состояний, нужна воспроизводимость/логирование переходов |
| MVP | Presenter дёргает View через интерфейс | Legacy; не предлагай как основной |
| MVC | — | Не предлагай (антипаттерн для мобильных клиентов) |

Ключевое, что хочет услышать интервьюер, — не название паттерна, а принципы:
**однонаправленный поток данных, единый immutable state экрана, отделение бизнес-логики
от UI, переживание config change и process death** (SavedStateHandle / `rememberSaveable`),
обработка одноразовых событий (events как часть state или Channel — назови trade-off).

#### Q: UI-фреймворк?

- **Jetpack Compose** — дефолт для нового кода; View/XML — legacy и interop.
- **Compose Multiplatform** — если решили шарить UI между Android/iOS (см. ветку KMP).
- Состояние экрана моделируй sealed-иерархией: `Loading / Content(data) / Error(retry)`;
  для списков — обязательно стабильные ключи элементов.

#### Q: Навигация?

- Android: Navigation Compose (type-safe маршруты); deep links — проговори, если у
  приложения есть нотификации (тап по пушу → конкретный экран + восстановление back stack).
- KMP: Decompose, Voyager или Navigation Compose Multiplatform.
- Большое приложение → навигация через интерфейсы фич-модулей (координатор/router),
  чтобы фичи не зависели друг от друга.

### 3.8 Фоновая работа

#### Q: Что должно выполняться, когда приложение не на экране?

Дерево решений (Android):

- **Отложимая гарантированная работа** (синк очереди, выгрузка логов, prefetch) →
  **WorkManager**: constraints (сеть/зарядка), backoff, chaining, уникальные работы.
  Переживает перезагрузку. Это ответ по умолчанию.
- **Точно во времени** (будильник, напоминание) → AlarmManager (`setExactAndAllowWhileIdle`)
  — только если действительно нужно точно; помни про Doze.
- **Видимая пользователю длительная работа** (плеер, трекинг маршрута, звонок) →
  Foreground Service с обязательным типом (mediaPlayback, location, dataSync…) и нотификацией.
- **Триггер извне** → FCM data message (high priority — экономно, Google троттлит).
- Учитывай **Doze mode / App Standby Buckets / ограничения фоновых сервисов** (API 26+),
  vendor-киллеры на китайских прошивках — поэтому дизайн «фон не гарантирован»:
  всё критичное должно догоняться при следующем запуске приложения.

### 3.9 Производительность

#### Q: Что оптимизируем? (спроси про бенчмарки: cold start, скролл, TTI)

- **Запуск:** App Startup, ленивая инициализация SDK (не всё в `Application.onCreate`),
  **Baseline Profiles** (+30% к cold start), splash по API SplashScreen. Метрики: TTID/TTFD.
- **Скролл/джанк:** не блокировать main thread (все IO — в корутины/Dispatchers.IO),
  downsampling картинок, стабильные ключи в LazyColumn, минимизация рекомпозиций
  (immutable-модели, `derivedStateOf`), Macrobenchmark + JankStats для измерения.
- **Память:** LeakCanary в debug, лимиты кэшей, `onTrimMemory`; большие Bitmap — главный враг.
- **Размер приложения:** App Bundle, R8/ProGuard, ресурсы WebP, dynamic feature modules
  для редких фич.
- **Правило для интервью:** сначала измерить (profile), потом оптимизировать; назови
  инструменты — Android Studio Profiler, Perfetto, Macrobenchmark.

### 3.10 Батарея и трафик

- **Радио — главный потребитель батареи**: батчи запросов вместо частых мелких
  (radio state machine дольше остаётся в high-power). Аналитика/логи — только батчами.
- Долгие соединения (WebSocket) рвать в фоне; polling — увеличивать интервал в фоне.
- Prefetch — только на Wi-Fi/зарядке (constraints WorkManager), уважай **Data Saver**
  (`isActiveNetworkMetered`).
- Сжатие: gzip/brotli на HTTP, protobuf вместо JSON при большом объёме, дельта-синк
  вместо полного.
- GPS: минимально необходимая точность и частота, fused location, геофенсинг вместо
  постоянного трекинга.

### 3.11 Безопасность и приватность

#### Q: Какие данные чувствительные и где они живут?

- **At rest:** токены/ключи → Keystore (hardware-backed) / Keychain; чувствительные поля
  БД → SQLCipher или шифрование полей; EncryptedSharedPreferences. Не хранить секреты
  в коде (декомпилируется), не логировать PII.
- **In transit:** только HTTPS/TLS; **certificate pinning** (OkHttp CertificatePinner) для
  банков/платежей — с планом ротации пинов (backup pins), иначе окирпичишь клиентов.
- **Клиент недоверенная среда:** вся авторизация и валидация — на сервере; цены, скидки,
  лимиты не считаем на клиенте; никогда на устройстве: обработка платежей, генерация
  купонов/билетов, антифрод-решения.
- Integrity: Play Integrity API / DeviceCheck против ботов и модифицированных клиентов.
- R8-обфускация, защита WebView (не включать JS-мосты без нужды), валидация deep links.
- **Приватность:** минимизация сбора, resettable pseudo-ID вместо device ID, GDPR/CCPA
  (согласие, right to be forgotten → эндпоинт удаления), permissions по необходимости
  и с graceful degradation (фото — через Photo Picker без permission вовсе).

### 3.12 Наблюдаемость, релизы, эксперименты

- **Крэши/ANR:** Crashlytics/Sentry; цель — crash-free rate > 99.9%.
- **Перфоманс в проде:** Firebase Performance / Play Vitals (startup, jank, ANR).
- **Аналитика:** свой Analytics-фасад поверх вендора; события батчатся и шлются
  через WorkManager (см. кейс Analytics SDK).
- **Логирование:** структурные логи, без PII, remote log level.
- **Релизы:** staged rollout (1% → 5% → 25% → 100%) с автооткатом по crash rate;
  **feature flags** для рискованных фич и всех 3rd-party SDK (возможность выключить
  без релиза — релиз в сторы не мгновенный и без отката «назад» у пользователя);
  A/B-эксперименты через remote config.
- Это любимая тема для **staff-уровня**: time-to-market, безопасный rollout,
  kill switches, деградация функциональности.

## 4. Ветка KMP — Kotlin Multiplatform

Заходи в эту ветку, если: (а) позиция KMP, (б) в требованиях Android + iOS общей командой,
(в) интервьюер спросил «как бы вы шарили код».

### 4.1 Q: Стоит ли вообще брать KMP в этом кейсе?

- **За:** одна бизнес-логика на две платформы (меньше рассинхрона и багов), Kotlin-команда,
  постепенное внедрение (можно начать с одного модуля), стабильный статус технологии,
  нативный UI остаётся нативным.
- **Против:** iOS-команде нужно жить с Kotlin-артефактом; тулчейн сложнее (сборка
  XCFramework, время компиляции Native); дебаг common-кода из Xcode ограничен;
  не всё из Jetpack доступно.
- **Рекомендация для интервью:** «шарю data + domain, UI решаю отдельно» — самый
  защищаемый вариант.

### 4.2 Q: Что шарим, что оставляем нативным?

```
┌──────────── androidApp ────────────┐  ┌──────────── iosApp ───────────────┐
│ Compose UI · Activity · платформа  │  │ SwiftUI · платформенные API       │
└──────────────────┬─────────────────┘  └──────────────────┬────────────────┘
                   └──────────────┬───────────────────────┘
                     ┌─────────── shared (commonMain) ───────────┐
                     │ Presentation (ViewModel/StateHolder)*     │
                     │ Domain: use cases, модели, бизнес-правила │
                     │ Data: Repository · Ktor · SQLDelight      │
                     │ androidMain / iosMain: expect-actual      │
                     └───────────────────────────────────────────┘
```

Уровни шаринга (назови как спектр):
1. **Только data/domain** (сеть, БД, бизнес-логика) — дефолт, минимальный риск.
2. **+ presentation** (общие ViewModel/StateHolder, состояние экранов) — UI дважды,
   но тонкий.
3. **+ UI через Compose Multiplatform** — максимальный шаринг; трейд-офф: менее
   «нативный» look&feel iOS, зависимость от зрелости CMP. Хорош для внутренних
   приложений, MVP, единого дизайн-кода.

### 4.3 Таблица технологий: Android-only ↔ KMP

| Задача | Android-only | KMP (commonMain) |
|---|---|---|
| HTTP | Retrofit + OkHttp | **Ktor Client** (движок OkHttp/Darwin) |
| Сериализация | Moshi/Gson/kotlinx | **kotlinx.serialization** |
| БД | Room | **SQLDelight** или Room KMP (2.7+) |
| Key-value | DataStore | multiplatform-settings / DataStore KMP |
| DI | Hilt/Dagger | **Koin**, kotlin-inject |
| Асинхронность | Coroutines/Flow | Coroutines/Flow (в Swift — через SKIE/KMP-NativeCoroutines) |
| Картинки | Coil/Glide | Coil 3, Kamel |
| Пагинация | Paging 3 | app.cash.paging (мультиплатформенный порт) |
| Навигация | Navigation Compose | Decompose / Voyager / Nav Compose MPP |
| Фоновые задачи | WorkManager | expect/actual: WorkManager ↔ BGTaskScheduler |
| Secure storage | Keystore + EncryptedSharedPrefs | expect/actual: Keystore ↔ Keychain |
| Дата/время | java.time | kotlinx-datetime |
| Файлы/IO | java.io | okio |
| Логи | Timber | Kermit, Napier |
| Крэши | Crashlytics | Crashlytics/Sentry KMP + CrashKiOS |
| Push | FCM | нативно на каждой платформе (FCM/APNs) + общий обработчик payload |

### 4.4 Q: Как достаём платформенное API из common-кода?

Два механизма — назови оба и trade-off:

- **expect/actual** — компилятор гарантирует реализацию на каждой платформе.
  Хорош для мелких утилит (UUID, версия ОС, путь к файлам).
- **Интерфейс в common + платформенная реализация через DI** — гибче, проще тестировать
  (подменяешь мок), не тянет механику компилятора. **Рекомендация для крупных вещей**
  (secure storage, connectivity monitor, background scheduler).

### 4.5 Что проговорить про iOS-interop (частые вопросы)

- Kotlin → Objective-C header: **generics стираются, suspend → completion handler,
  Flow не виден напрямую** → используем **SKIE** или KMP-NativeCoroutines, чтобы Swift
  получил async/await и AsyncSequence.
- Kotlin/Native memory model — новый (с 1.7.20) без «freeze», проблем со стейтом
  между потоками больше нет; старое ограничение упоминай как историю.
- Артефакт для iOS: XCFramework (+ SPM/CocoaPods дистрибуция), umbrella-модуль,
  бинарная совместимость — при обновлении shared нужен ребилд iOS.
- Размер бинаря iOS растёт от Kotlin runtime (~несколько МБ) — обычно приемлемо.

## 5. Типовые кейсы: прогон через фреймворк

Каждый кейс: главные вопросы → ключевые решения → «изюминка», которую ждёт интервьюер.

### 5.1 Лента (Twitter/Instagram feed)

- Вопросы: офлайн? real-time лайки? медиа? развивающиеся рынки?
- Решения: REST + **cursor-пагинация**; Room/SQLDelight = SSOT (лимит ~500 постов, LRU);
  Paging 3 + RemoteMediator; stale-while-revalidate; Coil + blurhash + prefetch;
  optimistic like с Idempotency-Key и откатом; SSE для live-счётчиков + FCM в фоне.
- Изюминка: consistency лайка между лентой и экраном деталей — единая запись в БД,
  оба экрана подписаны на неё (SSOT решает автоматически).

### 5.2 Чат / мессенджер

- Вопросы: 1:1 или группы (размер?), статусы доставки/прочтения, офлайн-отправка,
  несколько устройств, E2E-шифрование в скоупе?
- Решения: **WebSocket** (heartbeat, reconnect + backoff, resume по `last_message_id`)
  + FCM для фона; сообщения в БД со статусами `PENDING → SENT → DELIVERED → READ`;
  transactional outbox для отправки офлайн; client UUID для дедупликации; server-side
  sequence для порядка; пагинация истории — keyset назад от старейшего загруженного.
- Изюминка: multi-device sync (per-device `last_synced_id`, сервер хранит inbox);
  большие группы — fan-out на сервере, клиент лишь мержит дельты. E2E — упомяни
  Signal-style (ключи на устройстве, сервер видит шифртекст), не углубляясь без запроса.

### 5.3 File Downloader / Uploader Library

- Вопросы: размер файлов? параллельность? нужна ли докачка? прогресс в UI? работа в фоне?
- Решения: публичный API — `Downloader.enqueue(request): Handle` с listener/Flow прогресса;
  очередь с приоритетами и лимитом параллельных загрузок (например, 3);
  **HTTP Range / resumable** докачка, чанки, checksum-валидация; персистентная очередь
  (БД) — переживает смерть процесса; WorkManager для фона; политика ретраев с backoff;
  отмена и пауза; сегрегация по сети (wifi-only опция).
- Изюминка: жизненный цикл — кто владеет загрузкой, что при убийстве процесса;
  минимальные зависимости (это библиотека — не тащи Hilt наружу).

### 5.4 Image Loading Library (Glide своими руками)

- Решения: API `load(url).placeholder(...).into(view)`; конвейер: memory cache
  (LruCache) → disk cache (LRU, journaled) → сеть; дедупликация одинаковых in-flight
  запросов; downsampling под целевой размер; отмена при detach/recycle; пул Bitmap
  (reuse); приоритеты (видимые > prefetch); декодирование вне main thread.
- Изюминка: ключ кэша = URL + размер + трансформации; поведение при нехватке памяти
  (`onTrimMemory`).

### 5.5 Analytics SDK

- Решения: API `track(event, props)`; события пишутся в **локальную БД немедленно**
  (никогда не терять), отправка **батчами** (по количеству/таймеру/при запуске)
  через WorkManager; at-least-once + дедупликация по event UUID на сервере;
  сжатие батча; лимит хранилища с вытеснением старых; опциональный sampling.
- Изюминка: приватность (consent, PII-скраббинг), влияние на хост-приложение —
  минимум батареи/трафика, изолированные потоки, kill switch с сервера.

### 5.6 Кэширующая библиотека

- Решения: двухуровневая (memory + disk), API generic `get(key, loader)`,
  read-through + stale-while-revalidate; eviction LRU + TTL; журналирование диска
  (крэш-безопасность); потокобезопасность; статистика hit rate.

### 5.7 Location Sharing (карта курьера/друзей)

- Вопросы: точность? частота? фон? батарея? приватность?
- Решения: fused location, адаптивная частота (движется — чаще), батчинг точек,
  foreground service type location для активного шаринга; отправка по WebSocket/MQTT;
  на приёмной стороне — интерполяция маркера между точками; приватность: явный consent,
  TTL шаринга, обфускация точности где можно.

### 5.8 Фото-приложение с синхронизацией (Google Photos)

- Решения: локальная БД метаданных (MediaStore-скан) + resumable chunked upload
  через WorkManager (constraints: Wi-Fi/зарядка по настройке); хэш контента для
  дедупликации; очередь с приоритетами (новые фото раньше); thumbnails с сервера,
  оригинал по требованию; двусторонний delta-sync (`since=token`, tombstones для удалений).

### 5.9 Бронирование (билеты/отель) — строгая консистентность

- Решения: никакого optimistic UI на оплате; выбор места → **серверный лок с TTL**
  (например, 10 мин, таймер в UI); оплата — идемпотентный `POST /bookings`
  с Idempotency-Key (двойной тап/ретрай не создаст два платежа); статусная машина
  заказа с polling'ом/push для финального статуса; обработка «оплата прошла, ответ
  потерялся» — сверка по ключу при повторе.

### 5.10 Видео-лента / стриминг (TikTok/Stories)

- Решения: HLS/DASH + CDN; prefetch манифеста и первых сегментов следующих 1–2 видео;
  пул из 2–3 ExoPlayer; агрессивный маленький буфер старта; picture quality ladder
  по каналу; кэш сегментов (SimpleCache) с лимитом; телеметрия стартовой задержки
  и rebuffering rate.

## 6. Ошибки, критерии оценки, чеклист

### 6.1 Типовые ошибки кандидатов (из разборов реальных интервью)

1. Прыжок к решению без сбора требований.
2. «GitHub-template syndrome» — нарисовал заученные боксы Repository/ViewModel и не может
   объяснить, зачем они в этой задаче.
3. Over-engineering и самовольное расширение скоупа (YAGNI).
4. Молчаливое обдумывание — думай вслух.
5. Ответы «потому что так рекомендуется» вместо реальных причин.
6. Вендор-лок с порога («возьмём Firebase») до обсуждения архитектуры — сначала
   концепция (push provider, remote config), потом бренды.
7. Игнорирование сбоев: нет ретраев, нет обработки ошибок, нет плана на «сеть пропала
   на середине».
8. Критичная логика на клиенте (цены, платежи, валидация).
9. Блеф в незнакомой теме — честное «не знаю точно, но рассуждал бы так» ценится выше.
10. Нерешительность и постоянное «is this okay?».
11. Игнорирование подсказок интервьюера.
12. Недекларированные предположения — все допущения проговаривай явно.

### 6.2 Что оценивают по уровням

- **Middle:** уверенное владение конкретными паттернами и библиотеками, перевод
  high-level в детали, базовые trade-offs.
- **Senior:** архитектурный взгляд, взаимодействие компонентов, обоснованный выбор
  технологий, модульность/тестируемость, ведёт дискуссию сам.
- **Staff:** стратегия — аудитория, приоритеты бизнеса, time-to-market, безопасный
  rollout, приватность/легал, стоимость решения, влияние на команды, долгосрочные
  последствия.

### 6.3 Чеклист «пробежать в конце» (последние 2 минуты)

- [ ] Ошибки и ретраи: что при таймауте, 401, 429, 5xx?
- [ ] Офлайн: что видит пользователь без сети? что с его действиями?
- [ ] Процесс убит системой: что восстановится? (state, очереди, загрузки)
- [ ] Батарея/трафик: что жрёт больше всего и как ограничено?
- [ ] Безопасность: где токены, что шифруется, что нельзя на клиенте?
- [ ] Масштаб: что случится при 10× пользователей? (backoff, CDN, батчинг)
- [ ] Тестируемость: DI, интерфейсы на границах, фейки для сети/БД.
- [ ] Наблюдаемость: как узнаем, что фича сломалась в проде? kill switch?

## 7. Шпаргалка «проблема → решение»

| Проблема | Решение по умолчанию |
|---|---|
| Бесконечный список | Cursor-пагинация + Paging 3/RemoteMediator, БД = SSOT |
| Данные без сети | Room/SQLDelight как SSOT + stale-while-revalidate |
| Действия без сети | Transactional outbox + WorkManager + Idempotency-Key |
| Конфликт версий | Server authority + версии (409 → перечитать); LWW только для неважного |
| Real-time на экране | SSE (однонаправленно) / WebSocket (двунаправленно) |
| Real-time в фоне | FCM/APNs data push → подтянуть данные по API |
| Дубли мутаций | Client UUID + Idempotency-Key header |
| Шторм ретраев | Exponential backoff + jitter, Retry-After, лимит попыток |
| Токен протух | OkHttp Authenticator / Ktor Auth, refresh под mutex |
| Тяжёлые картинки | Coil: memory+disk LRU, downsampling, WebP/AVIF, CDN-ресайз |
| Большой файл вверх | Chunked resumable upload (tus-подобный) + WorkManager |
| Большой файл вниз | HTTP Range + персистентная очередь + checksum |
| Гарантированная фоновая работа | WorkManager (constraints, backoff, unique work) |
| Видео | Media3/ExoPlayer + HLS/DASH + prefetch + CDN |
| Секреты | Keystore/Keychain; в KMP — интерфейс + DI, реализации нативные |
| Аналитика | БД → батчи → WorkManager; at-least-once + дедуп |
| Опасный релиз | Feature flag + staged rollout + kill switch |
| Кроссплатформенная логика | KMP: Ktor + SQLDelight + kotlinx.serialization + Koin |
| Swift ↔ Kotlin async | SKIE / KMP-NativeCoroutines |
